01

技术选型与理由

核心原则：前后端分离，但只有一个 AI 网关。所有模型调用收敛在后端，前端只负责流式渲染和交互状态。这样密钥不落浏览器，成本与限流也好统一管。

层选型为什么是它（面试要能答出来）
前端框架Next.js 15（App Router）一个仓库同时容纳页面和 BFF 层，Server Component 天然适合先渲染文档列表再流式补内容。
前端样式Tailwind CSS + shadcn/ui组件源码在项目里可改，不用对抗库的设计系统。聊天类界面需要大量自定义，这点很关键。
流式交互Vercel AI SDK（ai + @ai-sdk/react）把 SSE 解析、增量渲染、中断、重试都封装好了。不要自己手写 EventSource——手写会遇到断线重连、POST 不能带 body 等一堆坑。
后端框架FastAPI + Python 3.12AI 生态在 Python，instructor、deepeval、langgraph 都是 Python 优先。异步原生，SSE 用 StreamingResponse 直接吐。
模型接入litellm统一 100+ 模型的调用格式，内建 fallback / 超时 / 预算。换模型只改配置。
编排langgraph问答和分流都需要「分支 + 置信度低转人工」的控制流，用图描述比 if-else 清晰，且可持久化状态。
检索fastembed + Qdrant（local 模式）本地 ONNX embedding，不需要 key、不需要 Docker；向量库跑嵌入式，数据落在 .qdrant/。实测后改的：原计划的 LightRAG 需要额外服务，而"零依赖可跑"对课程/实习项目更重要。量大再切 QDRANT_MODE=server。
结构化输出instructor + Pydantic工单分流的输出必须能直接入库，靠 prompt 约束不可靠，要 schema 校验 + 带错误重试。
可观测 / 评测langfuse + deepeval前者看线上 trace 和成本，后者做离线评测集回归。这两个是简历差异化的核心。
数据库SQLite（开发）→ Postgres（部署）SQLAlchemy 2.0 一套 ORM 两边通吃，切换只改连接串。
为什么不让 Next.js 直接调模型？因为要做成本控制、要做多模型 fallback、要落库 trace、要防 prompt 注入。这些都得在后端。前端直连只适合纯 demo，面试官一问「密钥怎么管」就露馅。

数据模型

四张核心表。注意 chunks 表只存元数据和向量 id，真正的向量在 Qdrant 里——这是常见的面试追问点（为什么不把向量存数据库？）。

-- documents：原始文档
CREATE TABLE documents (
  id           TEXT PRIMARY KEY,
  filename     TEXT NOT NULL,
  mime         TEXT NOT NULL,
  size_bytes   INTEGER NOT NULL,
  status       TEXT NOT NULL DEFAULT 'pending',  -- pending|parsing|indexed|failed
  error        TEXT,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- chunks：切片元数据（向量本体在 Qdrant，这里只存 id 映射）
CREATE TABLE chunks (
  id           TEXT PRIMARY KEY,           -- 与 Qdrant point_id 一致
  document_id  TEXT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  ordinal      INTEGER NOT NULL,           -- 在文档中的序号，用于回显上下文
  content      TEXT NOT NULL,
  page         INTEGER,
  token_count  INTEGER NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_chunks_doc ON chunks(document_id, ordinal);

-- tickets：工单 + 分流结果
CREATE TABLE tickets (
  id            TEXT PRIMARY KEY,
  title         TEXT NOT NULL,
  body          TEXT NOT NULL,
  category      TEXT,                      -- billing|account|bug|feature|other
  priority      TEXT,                      -- p0|p1|p2|p3
  confidence    REAL,                      -- 0~1，低于阈值转人工
  needs_human   BOOLEAN NOT NULL DEFAULT false,
  raw_llm       JSONB,                     -- 完整模型输出，便于 badcase 复盘
  corrected_by  TEXT,                      -- 人工纠正后的分类，做后续优化
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_tickets_cat ON tickets(category, created_at DESC);

-- conversations：会话与消息
CREATE TABLE conversations (
  id           TEXT PRIMARY KEY,
  title        TEXT,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE TABLE messages (
  id               TEXT PRIMARY KEY,
  conversation_id  TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  role             TEXT NOT NULL,          -- user|assistant
  content          TEXT NOT NULL,
  citations        JSONB,                  -- [{chunk_id, document_id, page, score}]
  prompt_tokens    INTEGER,
  completion_tokens INTEGER,
  cost_usd         NUMERIC(10,6),
  latency_ms       INTEGER,
  trace_id         TEXT,                   -- 对应 Langfuse
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);
为什么存 token / cost / latency 到消息表？因为这让你能在前端做一个「成本看板」，也能在简历里写「平均单次问答成本 $0.0031，缓存命中率 34%」。没有数据的项目没法量化，没量化的简历没有说服力。
06

API 契约

前后端先对齐这张表再动手，能省掉大量联调返工。所有接口前缀 /api/v1，统一错误格式 {code, message, trace_id}。

方法路径用途关键点
POST/documents上传文档multipart；立即返回 pending，解析走后台任务，前端轮询 status
GET/documents文档列表含 status 和 chunk 数，前端显示索引进度
DEL/documents/{id}删除文档级联删 chunks + Qdrant 向量，要保证一致
POST/chat/stream流式问答SSE；事件见下方；带 conversation_id 复用会话
POST/tickets提交工单同步返回分流结果，低置信度自动置 needs_human
GET/tickets工单列表按 category / needs_human 过滤，分页
POST/tickets/{id}/correct人工纠正分类写 corrected_by，作为后续优化依据
GET/metrics/summary成本与质量看板聚合 token / cost / 平均延迟 / 命中率

流式接口的事件设计——前端要能分别处理「文本增量」和「引用来源」两类数据，所以不能只吐纯文本：

# 请求
POST /api/v1/chat/stream
{ "conversation_id": "c_123", "message": "报销流程要几天？" }

# 响应（text/event-stream，逐条推送）
event: retrieval
data: {"hits": 3, "top_score": 0.82}

event: citation
data: {"chunk_id": "k_88", "document": "财务制度v3.pdf", "page": 12, "score": 0.82}

event: delta
data: {"text": "根据财务制度，普通报销"}

event: delta
data: {"text": "一般在 5 个工作日内到账。"}

event: done
data: {"message_id": "m_456", "tokens": {"in": 1240, "out": 86}, "cost_usd": 0.0021, "latency_ms": 1840, "trace_id": "lf_abc"}
易踩的坑：用 EventSource 无法发送 POST body，且不能自定义 header。所以要么改成 GET + query 传参（消息长了会超 URL 长度限制），要么用 fetch + ReadableStream 手动解析——这就是为什么建议直接用 Vercel AI SDK，它已经处理好了这些。
07

前端页面与状态

三个页面，但要处理的状态比页面多得多。这一节列的是「面试官会点开看」的细节。

页面核心交互必须处理的 5 个状态
聊天主页
/		 输入 → 流式输出 → 引用卡片可点开原文 ① 空态引导（给 3 个示例问题，别让用户面对空输入框）② 检索中（显示「正在查资料…」而非空白转圈）③ 流式输出中（打字机 + 可中断按钮）④ 未命中（明确说「文档里没找到」，不要硬编）⑤ 出错（可重试，保留已输出内容）
文档管理
/documents		 拖拽上传、进度轮询、删除 上传中 / 解析中 / 已索引 / 解析失败（给失败原因）/ 空列表引导
工单台
/tickets		 列表 + 分类筛选 + 低置信度高亮 + 一键纠正 加载骨架屏 / 空结果 / 待人工（醒目标记）/ 已纠正（显示原分类划掉）/ 分页加载
  • 引用溯源是这类产品的灵魂。每个回答下面列出引用的文档名 + 页码 + 相似度，点击能定位到原文片段。面试官看到这个会觉得你真的想过「用户凭什么信你」。
  • 流式中断必须做。用户改主意了要能停，且已输出的内容要保留。用 useChat 的 stop()，后端配合断开连接时终止生成（省 token）。
  • 骨架屏 > 转圈。列表类页面用骨架屏，感知延迟能降一半，这是纯前端功力，很容易被看见。
  • 类型要对齐。用 zod 定义一份 schema，后端 schemas.py 同名同结构。改接口时两边一起改，比口头约定靠谱。

简历怎么写

不要写「使用 LangChain 实现了 RAG 问答系统」。那种句子 HR 一天看八十遍。要写问题和结果，而不是技术名词。

✗ 弱写法
基于 LangChain + FastAPI + React 开发了知识库问答系统，
实现了文档上传、向量检索和流式回答功能。

✓ 强写法（三条，按这个结构）
· 面向内部文档分散、检索靠人翻的问题，搭建「解析-检索-生成」链路，
  支持 PDF/Word/网页混合入库；针对表格与跨页内容设计切片策略，
  50 条标注集上答案准确率从 62% 提升至 84%。

· 为控制成本引入统一模型网关与语义缓存，按问题复杂度分档路由，
  单次问答平均成本降至 $0.0031，重复问题命中缓存后延迟下降 61%；
  接入 Langfuse 全链路追踪，可定位到具体 chunk 的召回质量。

· 设计工单自动分流模块，用结构化输出约束保证分类结果可直接入库，
  6 分类准确率 91%；低置信度样本自动转人工并支持纠正回流，
  人工复核量下降约 40%。
注意每条的结构：「解决什么问题 → 我做了什么设计 → 可量化结果」。三个数字（84%、61%、91%）是这段简历真正的重量。数字不必好看，但必须真实且能解释来源——面试官一定会问「这个 84% 怎么测的」。
面试高频追问（前后端视角）：① 为什么用 SSE 不用 WebSocket？（单向流、基于 HTTP 无需额外协议、断线重连简单）② 流式输出中途用户关页面，后端怎么知道？（监听 disconnect，取消 task 省 token）③ 引用溯源怎么保证不指错？（chunk_id 与向量库 point_id 一致，回答时只允许引用本次召回集合内的 chunk）④ 上传大文件怎么不阻塞？（后台任务 + 状态轮询，不要同步解析）⑤ 向量库和业务库怎么保持一致？（删除时先软删业务记录再删向量，失败可补偿）
