01

简历 bullet（按岗位选一版）

同一个项目，投不同岗位要换不同的切入角度。不要三个版本都塞进简历，选一版，三条，占 4~5 行。

面向内部文档分散、检索靠人工翻找的问题，独立设计并实现「文档解析 → 向量检索 → 流式生成」服务； 支持 PDF/Word/Markdown 混合入库，5 条冒烟集准确率 100%（含 2 条防幻觉用例），无召回时主动拒答而非编造。
把模型调用收敛到统一网关（litellm），实现模型档位路由、超时重试、主备模型自动切换与按次成本记账； 单次问答成本 $0.0002，平均延迟 430ms，35 次调用累计 $0.0026，全部可查。
用 LangGraph 把问答拆成 rewrite / retrieve / grade / generate 四个可单测节点， 并自建轻量链路追踪（trace + span 落库），可回看每条候选的相似度与判分依据， 把 badcase 定位从「猜」变成「看是召回问题还是生成问题」。
独立完成前后端全栈交付：Next.js 15 + FastAPI，四个页面（问答 / 文档 / 工单 / 链路）， SSE 逐字流式输出 + 引用来源卡片，用户可中断生成且已输出内容不丢失。
设计 BFF 层统一转发：模型密钥只存在服务端，浏览器拿不到； /api/chat 保留 SSE 语义单独处理，其余 REST 走 rewrite 转发，避免把后端地址暴露给前端。
用无头浏览器（CDP）做端到端验证：真实点击 → 断言流式渲染、引用卡片、成本字段全部出现， 并沉淀为可复用的截图脚本；前端 tsc --noEmit 零错误。
构建可评测的 RAG 问答系统：本地 embedding（bge-small-zh-v1.5，512 维）+ Qdrant， 在冒烟集上准确率 100%，其中 2 条「语料中不存在的问题」正确拒答，验证了防幻觉设计。
实测发现密集检索的阈值陷阱：不相关问题相似度 0.41~0.47、真问题 0.50~0.74，单阈值切不干净； 改为三段式判分（≥0.60 直判、<0.35 直拒、中间交 LLM 判一次），把误召回压到 0， 额外成本约 100 token/次。
实现工单自动分流：用 instructor + Pydantic 做 schema 约束输出，置信度低于 0.7 自动转人工； 实测清晰工单 0.90~0.95 直接路由，模糊工单 0.25 进人工队列，并保留人工纠正回流数据。

03

60 秒演示脚本

录屏或现场演示都用这个顺序。先给结果，再给原理——面试官没耐心看你配置环境。

0-8s
打开问答页，直接点「报销流程需要几天？」
这是个知识库问答，先看效果：回答会逐字出来，下面带引用来源。
8-18s
等流式结束，鼠标指向引用卡片
每条引用标了文档名和匹配度，底部这行是模型、耗时、单次成本——这三个数都是真实记账，不是写死的。
18-28s
输入「公司股票代码是多少」
这个文档里没有。它不会硬编，而是明确说找不到，并且这一步根本不会调用模型——既防幻觉也省钱。
28-40s
切到链路页，展开刚才那条
这是我自建的追踪，能看到每一步。检索拿了两条候选，0.74 的直接判相关；刚才拒答那条是 0.46，被模型判成无关。
40-50s
切到工单页，提交一条模糊工单
第二个业务场景共用同一套底座：输出严格 JSON，置信度低于 0.7 自动标待人工，人工改了会回流。
50-60s
回到 README 的评测结果
最后是评测：5 条冒烟集全过，包括 2 条防幻觉用例。数字不大，但每个都能复现。
现场演示的保险做法：提前把后端跑起来、文档索引好，别在面试时上传文件。网络断了就切 LLM_MODE=mock——链路和 UI 完全一样，只是回答是固定文本，能保住演示不翻车。

两段自我介绍

30 秒版用于开场，2 分钟版用于「讲讲你这个项目」。

30 秒版
我做过一个内部知识库问答系统，前后端都是自己写的。它不只是调 API——我重点解决的是接进真实业务后的三个问题： 检索不准的时候怎么不瞎编、成本怎么控、出了问题怎么定位。为此我做了三段式判分、统一模型网关和自建链路追踪， 最后有评测集和成本数据能验证效果。
2 分钟版（结构：问题 → 方案 → 难点 → 结果）
「起因是内部文档散在共享盘和邮件里，找人问比搜索快，但人会请假。

我做了两层：一层是把文档解析、切片、向量化、检索、生成串成一条链路；另一层是工单自动分流，输出结构化 JSON 直接入库。 两个场景共用同一套模型网关和可观测设施。

中间最难的不是接模型，是判断「该不该答」。我一开始用相似度阈值，实测发现不相关问题也能拿 0.41~0.47， 跟真问题的 0.50 几乎贴着，加个问号就能掉到阈值以下。后来改成三段式：高置信直接答、低置信直接拒、中间让模型判一次。

结果是冒烟集 5/5，单次成本约 0.0015 元，所有调用都有 trace 可以回看。」
05

八个高频追问

括号里是对应的 ADR 编号，答的时候不用报编号，但心里要有底。

为什么不用现成的 RAG 框架（LangChain / Dify）？
用了 litellm 做网关、LangGraph 做编排，但没用 Chain 包住整个流程。原因是抽象层太重，出问题定位不到具体环节；而 Dify 这类可视化平台定制深度不够，讲不出架构取舍。我的判断标准是：能不能说清每个组件为什么在这。（ADR-001/002）
密集检索为什么还需要关键词召回？
两个作用：一是向量库挂了或没建索引时的降级兜底，否则所有问题都会变成"找不到"；二是为后面的混合检索留接口。代价是两种分数不同量纲，阈值必须分开配。（ADR-007/011）
为什么阈值是 0.6 / 0.35，不是 0.5？
实测出来的：真问题 0.50~0.74、不相关问题 0.41~0.47，中间地带太窄，单点切会误伤。所以设了一个"灰色区间"交给 LLM 判。换 embedding 模型这两个数必须重标定，我在配置里写了注释。（ADR-011）
LLM 判分不是又加了一次延迟和成本？
只对灰色地带的 top-1 判，约 100 token、0.6 秒；高置信度的直接放行不调模型。相比之下，把真问题判成"找不到"对用户的伤害更大，所以这个交换是划算的。
为什么不用 Langfuse？
它需要一整套服务端（Postgres + Web + Docker）。我的目标是 clone 下来就能跑，所以自己写了轻量 trace，接口对齐 OTel span 语义，要换只替换 Tracer 实现。而且我要的粒度是"每个候选为什么被丢"，这个 Langfuse 默认视图不直接给。（ADR-013）
流式输出用户中途关页面，后端怎么办？
监听 disconnect，取消 asyncio task，已生成的部分照样落库。这样既省 token，用户回来也能看到答到一半的内容。（chat.py）
向量库和业务库怎么保证一致？
删除时先删向量再删业务记录。反过来的话，业务记录没了、向量还在，用户搜到的引用会指向不存在的文档。向量删失败只是留下孤儿数据，可以后台清理，用户无感。（ADR-005）
如果文档量涨到 100 万份？
三件事：切片和索引离线化、向量库从 local 切 server 模式并分片、召回改两级（粗排 top-100 再精排）。关键词召回那套 SQL 扫描要换成 FTS 或 BM25，现在这个实现只适合万级以下。
06

别吹的三件事

不要说「准确率 100%」而不加限定。5 条用例的 100% 和 500 条的 100% 是两回事。说「5 条冒烟集全过，包括 2 条防幻觉用例」，比一个孤零零的 100% 可信得多。
不要说「生产级」「高并发」。这是个单机项目，没压测、没多副本、没灰度。被追问一句"QPS 多少"就露馅了。说「完整链路可跑通、有评测和可观测」，是实话也够用。
不要隐瞒没做的部分。生产构建没在本机验证通过、Qdrant 只用过 local 模式、没有真实用户——这些主动说出来，反而证明你知道边界在哪。面试官最怕的不是你没做过，是你把没做过的说成做过了。
