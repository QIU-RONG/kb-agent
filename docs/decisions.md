# 技术决策记录（ADR）

> 面试时最有用的材料。每做一个取舍就在这里写一段：**当时有哪些选项、为什么选这个、代价是什么**。
> 面试官问「为什么用 A 不用 B」时，你能翻出这段就是真实经历；答不上来就是照着教程做的。

格式：背景 → 选项 → 决定 → 代价。

---

## ADR-001 前后端分离，模型调用全部收在后端

**背景**：Next.js 也能直接调模型（Server Action 里就行），似乎更省事。

**选项**
1. 前端直连模型：少一跳，代码最少
2. 后端统一网关：多一层，但能管住密钥、成本、限流、trace

**决定**：选 2。密钥不能进浏览器；成本要按用户维度记账；出问题要能查 trace。

**代价**：多一次网络跳转（本地约 2ms，可忽略）；要多维护一套 Python 服务。

---

## ADR-002 SSE 而非 WebSocket

**背景**：问答需要流式输出。

**选项**
1. WebSocket：双向，但要维护连接状态、心跳、重连
2. SSE：单向，基于 HTTP，断线浏览器自动重连

**决定**：SSE。问答是「请求-流式响应」模型，不需要双向；SSE 能直接穿过大多数网关和 CDN。

**代价**：不能主动推消息（比如「文档索引完成」通知），这类需求得另走轮询。

---

## ADR-003 向量存 Qdrant，不存 Postgres

**背景**：业务数据已经在 Postgres，能否用 pgvector 一并存掉？

**选项**
1. pgvector：少一个组件，事务一致性好
2. Qdrant：专用向量库，HNSW 索引 + payload 过滤

**决定**：选 2。检索需要「向量相似 + 元数据过滤」组合，Qdrant 的过滤性能明显更好。

**代价**：多一个组件要部署；删除文档时要保证业务表和向量库一致（见 ADR-005）。

---

## ADR-004 无召回时不调模型

**背景**：检索为空时，是否让模型「凭知识回答」？

**决定**：不调。直接返回固定的降级话术。

**理由**：这是幻觉的主要来源。宁可说「没找到」，也不给一个看起来合理但没依据的答案——真实业务里后者代价高得多。顺带省一次调用成本。

**代价**：某些「常识类」问题体验变差（比如问「你是谁」）。可通过白名单放行少量通用问题缓解。

---

## ADR-005 删除文档的顺序：先删向量，再删业务记录

**背景**：两个存储，删除必然有中间态。

**决定**：先删向量。失败就中止，业务记录保留。

**理由**：如果反过来，业务表记录没了、向量还在，用户搜到的引用会指向不存在的文档（前端直接 404）。而向量删失败只是留下孤儿数据，可以后台补偿清理，用户无感。

**代价**：需要写一个定期清理孤儿的任务。

---

## ADR-006 切片按字符而非按 token

**背景**：切片大小按什么单位衡量？

**决定**：先按字符（chunk_size=600, overlap=80），第 2 周实测后再决定是否换 token 计数。

**理由**：字符切分零依赖、可预测；中文场景下字符与 token 的比例相对稳定，误差可接受。

**代价**：token 数会波动，极端长文本可能超出上下文预算。第 3 周引入 tiktoken 精确计数。

---

## ADR-007 关键词召回用独立阈值（实测踩出来的）

**背景**：加关键词降级检索后，「年假可以跨年结转吗」明明文档里有答案，却走了"找不到"分支。

**排查**：查 trace 发现召回得分 0.25，被统一的 0.35 阈值挡掉了。而向量检索的 0.57 能过。

**根因**：两种分数的量纲根本不同——
- 余弦相似度天然落在 0.3~0.9
- 2-gram 命中率 = 命中词数 / 总词数，长查询会被系统性稀释（8 个 2-gram 命中 2 个 = 0.25）

**决定**：`Hit` 增加 `source` 字段，判分时按来源用不同阈值（vector 0.35 / keyword 0.22）。

**代价**：两套阈值都要各自校准；将来加第三种召回（如 BM25）还要再加一套。
更彻底的做法是把分数统一映射到 0~1 的"相关性概率"，但那需要标注数据，第 3 周再做。

**面试价值**：这类"看起来能跑但效果不对"的问题，比"我实现了 RAG"更能证明你真跑过数据。

---

## ADR-008 没有 embedding key 时直接走关键词，而不是硬调再失败

**背景**：接真实模型后，日志每次请求都刷一条
`vector search unavailable: Missing credentials`。功能没坏（有降级），但每次都要白等一次超时。

**根因**：`embed_texts` 用的是 `openai/text-embedding-3-small`，而项目只配了 DeepSeek 的 key。
DeepSeek 不提供 embedding 接口，所以这条路必然失败。

**决定**：`rag.search` 先检查 `_embedding_available()`，没 key 就直接走关键词召回，不发请求。
embedding 模型抽成 `EMBED_MODEL` 配置项。

**代价**：用户可能不知道自己在用降级检索。所以 `/health` 和检索事件里都带上 `source` 字段，
一眼能看出这次是 `vector` 还是 `keyword`。

---

## ADR-009 黄金集必须和语料对齐（实测踩出来的）

**背景**：第一次跑评测 80%，唯一失败的是「新员工入职要准备哪些材料」。

**排查**：不是模型答错，是样例文档里根本没写入职内容，系统正确地说了「没有找到」。

**决定**：把该用例换成语料里确实有的「一线城市住宿标准是多少」，并在测试文件里写明
「加用例前先确认语料里有对应段落」。

**教训**：**评测集错了比系统错了更危险**——它会让你去优化一个不存在的问题。
真实项目里应该有个校验：每条 has_answer=True 的用例，先确认检索能召回相关 chunk。

## ADR-010 高置信度阈值不适用于 p0 工单（待校准）

**背景**：实测「全员无法登录，所有业务都停了」被判 `account / p0 / confidence 0.60`，
因为 0.6 < 0.7 被标为「待人工」。

**问题**：紧急故障进人工队列等待，比误分类的代价更高。

**候选方案**
1. `priority == "p0"` 时不因置信度阻塞路由，但保留复核标记（需要加一个 `review_required` 字段）
2. 阈值按优先级分档：p0 用 0.4，p2 用 0.8

**当前状态**：未改。因为两种方案都要额外字段或额外配置，属于第 2 周做评测校准时的任务。
**这类"知道有问题但先记录、不急着改"的判断，本身就是工程取舍的一部分。**

## ADR-011 向量检索用「两段式判分」，不用单阈值

**背景**：接上本地 embedding（bge-small-zh-v1.5）后，密集检索永远会返回 top-k，
哪怕问题跟语料毫无关系。原本 0.35 的阈值形同虚设——「公司股票代码是多少」拿了 0.4657 被当成命中。

**实测分布**（样例语料，10 条问题）

| 类型 | 相似度区间 |
|---|---|
| 真相关问题 | 0.50 ~ 0.74 |
| 不相关问题 | 0.41 ~ 0.47 |

两类几乎贴在一起。更糟的是同一句话加不加问号都能让分数从 0.5257 掉到 0.50 以下。

**决定**：三段式
- `>= 0.60` → 直接判相关，不调模型
- `< 0.35` → 直接判无关
- 中间 → 让 fast 档模型判断「这段资料能否回答问题」，只判 top-1

**效果**：5 条评测集从 80% 回到 100%；「一线城市住宿标准是多少？」(0.4828) 被救回，
「公司股票代码」(0.4657) 和「怎么申请专利」(0.4053) 被正确拒掉。

**代价**：灰色地带的查询多一次约 100 token 的调用（< $0.00003），延迟增加约 0.6s。
判分失败时保守放行——宁可多给一段资料，也别把真问题判成"找不到"。

## ADR-012 向量库用 local 模式，embedding 用本地模型

**背景**：机器上没有 Docker，也没有 OpenAI key（只有 DeepSeek，而它不提供 embedding 接口）。

**决定**
- Qdrant 用 `QdrantClient(path=...)` 嵌入式模式，数据落在 `.qdrant/` 目录，不需要任何外部服务
- embedding 用 `fastembed` + `BAAI/bge-small-zh-v1.5`（512 维，ONNX，90MB），CPU 推理

**代价**
- 嵌入式模式有文件锁，只能单进程访问 → client 做成模块级单例，且不主动 close
- 首次要下模型；本地 ONNX 推理比 API 慢（单条约 20~50ms，可接受）
- 数据量大了必须换 server 模式，改 `QDRANT_MODE=server` 即可

**面试价值**：这套组合让项目**零外部依赖可跑**——没有 Docker、没有 embedding key 也能演示完整向量检索。
真实项目里"能在别人机器上一键跑起来"本身就是工程能力。

## ADR-013 自建轻量 trace，而不是接 Langfuse

**背景**：可观测性是这类项目的核心价值之一（"你怎么定位一个 badcase"），
原计划用 Langfuse。但 Langfuse 需要一整套服务端（Postgres + Web + Docker），
这台机器没有 Docker，也不想让使用者先去注册账号。

**决定**：自己写 `core/tracing.py`，把每一步落进 SQLite 两张表（`traces` / `spans`），
前端加一个 `/traces` 页面直接看。接口刻意对齐 OpenTelemetry 的 span 语义，
以后要换 Langfuse 只需替换 `Tracer` 实现。

**记录内容**（这些正是定位问题需要的）：
- `rewrite`：改写后的 query，或"跳过改写"的原因
- `retrieve`：原始候选数、来源（vector/keyword）、每条候选的得分
- `grade`：**每个候选的判决**——被阈值挡掉 / 被 LLM 判无关 / 保留
- `generate`：模型、token、成本、耗时

**代价**：没有 Langfuse 的聚合面板、告警、数据集管理。
**收益**：零依赖可跑，且 `grade.verdicts` 这个粒度比 Langfuse 默认视图更贴这个项目的需要——
一眼能看出"是召回没给对"还是"给了对的但模型答歪了"。
